🎓 Academia — Guía de Arranque & Swagger

Microservicios Spring Boot 4 + API Gateway + MySQL · todo se accede por el gateway en :8080

1. Arrancar el proyecto

Requisitos: solo Docker Desktop. No necesitas Java ni Maven instalados — cada servicio se compila dentro de Docker (build multi-stage).

Desde la raíz del repositorio:

# Construir e iniciar todo (primera vez o tras cambios de código)
docker compose up --build -d

# Iniciar sin reconstruir
docker compose up -d

# Ver estado de los contenedores
docker compose ps

# Ver logs de un servicio
docker compose logs -f auth-service

# Reconstruir/reiniciar un solo servicio
docker compose up --build -d clases-service

# Detener todo
docker compose down
Los scripts build-all.bat / clean-all.bat ya no existen y no se usan: docker compose los reemplaza por completo.

2. Cómo funciona la autenticación (¡léelo primero!)

  1. Registro → POST /api/auth/registrar con run + clave. público
  2. Login → POST /api/auth/login devuelve un JWT (HS256, válido 1 hora). público
  3. Llamadas protegidas → cualquier otra ruta /api/** exige cabecera Authorization: Bearer <token>. El gateway valida el token y lo reenvía; el servicio lo vuelve a validar.
Ruta¿Token?
/api/auth/**No (público)
/swagger-ui.html, /v3/api-docs/**No (público)
Todo lo demás /api/**Sí — Bearer JWT

3. Usar la API desde Postman

Paso 1 — Registrar un usuario

POST http://localhost:8080/api/auth/registrar
Content-Type: application/json

{
  "run": "11111111-1",
  "clave": "secreta123"
}

Respuesta: { "message": "¡Usuario creado exitosamente!" }

Paso 2 — Login y obtener el token

POST http://localhost:8080/api/auth/login
Content-Type: application/json

{
  "run": "11111111-1",
  "clave": "secreta123"
}

Respuesta:

{
  "status": "ok",
  "token": "eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxMTExMTExMS0xIiwi..."
}

Paso 3 — Llamar a un endpoint protegido

Pestaña Authorization → Type Bearer Token → pega el token. O bien a mano:

GET http://localhost:8080/api/clases/listar
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxMTExMTExMS0x...
Ojo con la ruta y el método exactos. Cada controller define sus propias rutas; muchas listas son /listar y no la ruta base. Si llamas a la ruta/método equivocados verás un 500 (varios servicios envuelven el 404/405 como 500). Usa Swagger para ver la ruta y verbo correctos.

Atajo útil en Postman: en la request de login, pestaña Tests, guarda el token en una variable: 
pm.environment.set("token", pm.response.json().token);
Luego en las demás requests usa Authorization: Bearer {{token}} y no tendrás que copiarlo cada vez.

Matices (nuances) de Postman

  • Usa siempre http://localhost:8080 (el gateway), no los puertos 808x directos.
  • El token expira en 1 hora → si empiezas a recibir 401, vuelve a hacer login.
  • 401 = token ausente/ inválido/ expirado.   403 = autenticado pero sin permiso.   404 = ruta no mapeada en el gateway.
  • No olvides Content-Type: application/json en los POST.

4. Usar Swagger (agregado en el gateway)

Abre en el navegador:

http://localhost:8080/swagger-ui.html
  1. Arriba a la derecha hay un desplegable para elegir el servicio (1. Auth, 2. Calificaciones, … 8. Usuarios). Cada uno carga su documentación vía el gateway.
  2. Para endpoints protegidos: primero ejecuta POST /api/auth/login desde el propio Swagger (servicio "Auth") y copia el token.
  3. Pulsa el botón Authorize 🔒 (arriba a la derecha), pega solo el token (sin la palabra Bearer; el esquema bearerAuth ya la añade) y confirma.
  4. Ahora usa Try it out → Execute en cualquier endpoint; Swagger enviará el header Authorization: Bearer … automáticamente.

Matices (nuances) de Swagger

  • El Swagger del gateway agrega los docs de todos los servicios; cada servicio expone su propio /v3/api-docs y el gateway los reescribe a /v3/api-docs/<servicio>.
  • /swagger-ui.html responde 302 redirigiendo a /swagger-ui/index.html — es normal.
  • El botón Authorize aplica el token a todas las llamadas de esa pestaña hasta que cierres el navegador o pulses Logout.
  • Si el token expira (1 h), Swagger empezará a devolver 401 → vuelve a Authorize con un token nuevo.
  • Las rutas de "Try it out" salen por el gateway :8080, así que respetan el ruteo y la seguridad reales.

5. Problemas conocidos / Troubleshooting

SíntomaCausa / solución
401 en todo con token válidoToken expirado (1 h) → re-login. Verifica que apuntas a :8080.
500 en un GET que "debería existir" Casi siempre es ruta o verbo incorrecto (p. ej. /api/clases en vez de /api/clases/listar); algunos controllers devuelven 404/405 como 500. Revisa la ruta exacta en Swagger.
Tablas semilla vacías El data.sql solo se carga con spring.sql.init.mode=always. Ya está activado en los servicios con semillas (clases, inscripciones, evaluaciones, pago, user); los inserts usan INSERT IGNORE (re-ejecutables).
Un servicio queda Exited (1)docker compose logs <servicio> para ver el stack trace.
Cambié código y no se reflejaReconstruye: docker compose up --build -d <servicio>.
Quiero empezar con BD limpia docker exec mysql mysql -uroot -proot -e "DROP DATABASE academia_noafer; CREATE DATABASE academia_noafer;" y reinicia los servicios.
Arquitectura en una línea: el gateway (8080) es la única entrada; valida el JWT y rutea a cada microservicio; todos comparten la BD academia_noafer y validan el mismo token (HS256, secreto en JWT_SECRET/SECRET). La identidad de credenciales vive en auth_usuarios (auth-service) y el perfil en usuarios (user-service), unidos por run.
